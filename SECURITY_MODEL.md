# GPCC Security & Privilege Model

## Access sequence

1. Visitor opens the application.
2. Only the **Secure Account** surface is available.
3. User logs in or signs up.
4. Signup creates `Member + Pending` automatically.
5. An Administrator approves the account.
6. Middleware verifies the session and approval status.
7. Middleware verifies route privilege.
8. The client shell renders only modules allowed for the user's role.
9. Supabase RLS independently enforces the same privilege rules at database level.
10. Financial changes are written to the immutable audit trail by database triggers.

## Roles

| Role | Access |
|---|---|
| Administrator | Full system, user management, master setup, audit logs |
| Editor | Financial entry/update/delete, transfers, reports, Excel import |
| Member | Dashboard + reports/read-only |
| Pending/Rejected/Inactive | No application access |

## Important security properties

- No public financial pages.
- Direct URL navigation is protected by middleware.
- Browser-side UI restrictions are not treated as the security boundary.
- RLS is the final data-access boundary.
- Users cannot self-approve or self-promote through the browser.
- New accounts cannot insert financial data until approved.
- `created_by` is stamped from `auth.uid()` on insert; the browser cannot impersonate another actor.
- Audit records are generated by a `SECURITY DEFINER` database trigger.
- Normal authenticated users have no INSERT/UPDATE/DELETE policy on `audit_logs`.
- Permission definitions are read-only from the browser.
- Excel import API verifies authentication and the `excel/import` permission before reading a file.

## Supabase setup

Run `supabase/schema.sql` in the Supabase SQL Editor.

Then verify:

- Email/password authentication is enabled.
- The `profiles` trigger exists on `auth.users`.
- RLS is enabled on all application tables.
- The first Administrator account is created/approved using a controlled admin process.

### First administrator

For the first deployment, create one account through Sign Up. In Supabase, approve that user's profile and set:

- `status = 'Approved'`
- `role = 'Administrator'`

After that, all subsequent accounts should be approved through the application's administration workflow.

> Do not expose the Supabase service-role key to the browser. This project intentionally uses the public anon key on the client and relies on RLS.
